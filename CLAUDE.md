# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This file scopes guidance to the `repair/` frontend. The root `RepByRep/CLAUDE.md` covers the backend (`Server/`) and the sibling `client/` app — read it first when a task crosses the wire, since the GraphQL contract, auth model, and resolver inventory all live on the server side.

## What this app is

`repair/` is the **e-commerce frontend** for the "repair" clothing-store system described in the project brief. It is the **only** frontend for that system — there is no separate admin app. The four user roles in the requirements (Customer, Admin, Delivery, Accounting) are all served by this same Next.js app, gated by role at runtime. The sibling `client/` directory is a different product (RepByRep forms); do not import from it or copy patterns out of it.

This app talks exclusively to the **`repair` sub-server** at `POST /repair/graphql`. Do **not** point requests at `/form/graphql` — that is the formServer sub-server for the other product, with a different user model, different schema, and no e-commerce resolvers.

## Current state

Auth and marketing surfaces are largely presentational. The landing header fetches live data from the backend (the first GraphQL call wired up from this app). The customer storefront's `/shop` page is **wired to the backend end-to-end**: category tree, product grid, **facet filtering** (size/color/material/item-type/price — options + bounds from `myAppListColors`/`myAppListSizes`/`myAppListMaterials`/`myAppGetPriceRange`, applied server-side via `myAppListProducts`), **pagination** (`?page=`, `{items,total}`), product detail, the **add-to-cart drawer** (real colors/sizes/stock from `myAppGetProductDetail`; ADD persists to guest localStorage or the DB cart), the **`/cart` page** (`useCart` hook + live totals), and the **search overlay** (`myAppListProducts({search})`). `src/lib/mockShop.js` survives only as a fallback for the filter-drawer option labels + a few derived helpers. The **`/checkout` details page (step 2) is now wired end-to-end**: `useCart` items + **method-aware totals**, **live delivery methods + tax** from `myAppGetCommerceSettings` (`buildDeliveryMethods` in `cartTotals.js` — enabled methods only, express double-gated), logged-in **saved addresses** via `myAppGetMyAddresses`/`myAppAddAddress` (`useAddresses` hook), and a **guest-registration flow** (`myAppSignUp` + `mergeGuestCartThenSync` + `myAppAddAddress` on Continue). The **`/checkout/payment` step (step 3) and `/checkout/success` are now wired too**: payment places a real order via `myAppCheckout` (payment methods from the admin commerce settings, address from the details step), and success reads the resulting `lastOrder` + `myAppGetOrderDetail`. The payment page shows the user's **saved cards** (demo, client-side) + admin-enabled wallets/COD with an **ADD NEW CARD** button (`AddCardDrawer`), so a freshly-registered user can add a card and pay. A **DEMO payment gateway** (`DemoPaymentGateway.jsx`, a clearly-labeled sandbox modal — no real processor) sits in front of order placement: Confirm & Pay opens it for card/wallet methods (COD skips it), an approval places the real order via `myAppCheckout`, and a (simulated) decline routes to **`/checkout/failed`** — which is now also wired, reading the declined attempt (amount / last4 / txn / reason from the store's transient `paymentAttempt`) + the live cart. Notes:
- **`/shop` never shows an all-products listing.** When `?category=` is absent, render `CategoryPicker` so the user always commits to a major category before seeing products. This is a deliberate product decision — don't add an "all products" page back.
- Browse and filter state lives in **query params on `/shop`**, not nested path segments. Adding facets later (color, size, price, sort) follows the same pattern — append query params, don't add new path segments.

## Conventions

- **JavaScript, not TypeScript.** `jsconfig.json` is the only config; do not introduce `.ts`/`.tsx` files or a `tsconfig.json` without discussing it. (Note: the sibling `client/` app is TypeScript — do not copy its patterns wholesale.)
- **Path alias `@/*` → `./src/*`** (`jsconfig.json`). Use it for cross-folder imports instead of long relative paths.
- **React Compiler is enabled** (`next.config.mjs` → `reactCompiler: true`). Don't hand-write `useMemo` / `useCallback` for things the compiler can hoist; reach for them only when profiling shows a real issue.
- **React Compiler + ternary guards — use optional chaining defensively.** The compiler's memoization analysis can pre-evaluate both branches of a ternary expression, so an "obviously guarded" access like `{state ? <X title={state.kind} /> : null}` can still throw `Cannot read properties of null (reading 'kind')` at runtime when `state` is null. **Use `state?.kind` (or hoist a guard `if (!state) return …`) even inside branches you think are protected.** This bit `CategoryManager` on initial render and required the same pattern across every admin manager component — see `src/components/admin/categories/CategoryManager.jsx` for the canonical fix (guard at the top of the save handler, `?.` on every `editing.X` access, and `{open && editing ? …}` instead of `{open ? …}` for the drawer body).
- **Effect data-fetch under React Strict Mode — never pair a "run-once" ref guard WITH a `cancelled` flag.** Strict Mode (dev) mounts → unmounts → remounts. If a mount effect both (a) early-returns on a `mountedRef.current` guard so it "only runs once" AND (b) registers a cleanup that flips a `cancelled` flag the async body checks before `setState`, they deadlock: the first cleanup sets `cancelled = true`, the second mount is blocked by the ref guard so it never starts a fresh request, and the one in-flight request bails before clearing `loading` → the page hangs on "Loading…" forever (no data, no error). **Pick ONE:** rely on the `cancelled` flag alone (the double mount fires two requests; the first is ignored, the second resolves normally — fine for an idempotent read), and do NOT add a run-once ref on top. This bit `WishlistInsightsManager` — see the comment on its mount effect.
- **Server→client function-prop boundary.** Server components can't pass functions to client components — Next.js production builds throw `Functions cannot be passed directly to Client Components` and the page fails to prerender. The dashboard hits this with `DataTable`'s `columns` array (each column has a `render: (row) => …` callback). **Pattern:** when a server page needs a `DataTable`, render a tiny `"use client"` wrapper component that owns the column definitions and accepts plain `rows={…}` from the server — see `src/components/admin/dashboard/RecentOrdersTable.jsx`. Manager pages (Products, Orders, etc.) don't need this because they're already client components.
- **Tailwind v4** via `@tailwindcss/postcss`. There is no `tailwind.config.js` — theme tokens live in `globals.css` under `@theme inline { ... }`. Add new design tokens there, not in a JS config file. There is **no animation library** — splash uses `@keyframes` in `globals.css` plus inline `animation:` styles, and that's the established pattern. Don't add framer-motion / gsap / etc. without discussing.
- **Tailwind v4 + Turbopack gotcha:** arbitrary `aspect-[w/h]` classes (e.g. `aspect-[176/264]`) silently don't apply under the current Turbopack content scanner — the parent collapses to zero height and `next/image` with `fill` renders nothing. Use inline `style={{ aspectRatio: "176 / 264" }}` for image card containers. `bg-[#hex]` / `text-[#hex]` arbitrary values work fine for non-toggled classes, but conditional arbitrary classes inside template literals can also miss the scanner — when a sale price chip or strikethrough needs to toggle, prefer inline `style` (`backgroundColor`, `textDecoration`) over a conditional `bg-[#1d4ed8]` / `line-through` class. See `customer/shop/ProductCard.jsx` for the pattern. **The same scanner gotcha extends to positioning/sizing/outline arbitraries** — at least these forms have all been observed being silently dropped in `customer/cart/CartPageClient.jsx`: `top-[Npx]`, `left-[Npx]`, `right-[Npx]`, `w-[Npx]`, `h-[Npx]`, `outline-[#hex]`, `-outline-offset-1`, and even non-arbitrary classes like `w-64` in some contexts. Symptoms: an absolutely-positioned line collapses to width 0, an outlined card shows the default text color as its outline, a stepper connector lines up at `top: 0` instead of the intended Y. **Pattern:** for any absolutely-positioned divider, decorative element, or outlined surface, default to inline `style` for `left/right/top/width/height/outlineColor/outlineOffset` from the start — don't trust arbitrary positioning/outline classes here. See the multiple `style={{ left, top, width, height }}` and `style={{ outlineColor: "#…", outlineOffset: "-1px" }}` usages in `CartPageClient.jsx` for the canonical fix.
- **Card overlays escaping above page-level overlays — `isolate` the card.** A `relative` element with NO `z-index` does NOT create a stacking context, so an absolutely-positioned descendant with a `z-index` (e.g. `ProductCard`'s `LabelBadges` at `z-20`) participates in the ROOT stacking context and can paint ABOVE a sibling page-level overlay (the desktop `SearchOverlay` is also `z-20`, mounted earlier in the DOM, so the grid's labels bled through it). Fix: add `isolate` (`isolation: isolate`) to the card's image wrapper so its internal `z-10`/`z-20` are scoped to the card; the card then sits at root `z-auto`, below any fixed overlay (search/filter drawer/add-to-cart). Don't fix this by z-index-juggling the overlays — `isolate` on the card is the general fix. See `customer/shop/ProductCard.jsx` (`group relative isolate …`).
- **Responsive widths between `md` and Figma design width — flex, don't pin `lg:` widths.** Figma desktop frames are ~1376–1440 wide; pinning a child to `lg:w-[508px]` / `lg:w-[545.33px]` / etc. only works once the viewport reaches the Figma width plus padding, so every viewport between `lg` (1024) and ~1500 overflows. The pattern that works is `flex-1 min-w-0` on the flex children plus `lg:max-w-[<figma-width>]` as a ceiling — the layout fluidly fills whatever space the section's `max-w-[1376px]` and section-level padding leave, and only locks to the Figma proportions at the widest viewports. This caused the original `/products/[slug]` hero to overflow by 269px at `lg` and 109px at `xl`; the fix is in `customer/product/ProductPageClient.jsx`. Apply the same pattern when porting any Figma desktop hero into code.
- **Responsive typography ramps `md → lg → xl`, don't jump straight to Figma sizes at `md`.** When a section has very different mobile vs desktop type scales (e.g. 24px → 48px heading, 36px → 72px stat numbers), use an intermediate `md:` size, an `lg:` size, and the Figma value only at `xl:`. Otherwise the section reads as "shrunken Figma" between 768 and ~1280. The "Crafted to Last" section in `customer/product/ProductPageClient.jsx` is the worked example — see the heading + stat-value class lists for the ramp shape.
- **App Router only.** No `pages/` directory; don't add one.
- **`viewport` export in `src/app/layout.js` is load-bearing.** Without it, the page is missing `<meta name="viewport" content="width=device-width, initial-scale=1">` and mobile browsers (plus any headless screenshot tool) lay out at the legacy 980px default — every storefront page then renders content wider than the visual viewport and clips on the right. The fix is the App Router idiomatic `export const viewport = { width: "device-width", initialScale: 1 }` already in the root layout; don't remove it.
- **Figma SVG export NaN bug.** When the Figma MCP `get_design_context` API returns SVG assets, complex paths occasionally serialize a degenerate cubic curve as the literal text `Cnan nan` inside the `d` attribute. That's invalid SVG path syntax, so the renderer stops at the first invalid command — the icon ends up as a fragment of the original mark (Mastercard rendered as just two dots, Apple Pay cut off mid-"Pay", etc.). **Pattern:** before trusting any SVG downloaded from Figma's MCP, `grep -c nan` it. If it has `nan`, fall back to the PNG via the `get_screenshot` MCP API on the same node id — the screenshot pipeline rasterizes correctly because it bypasses path serialization. The 6 payment icons in `repair/public/cart/` are the worked example: `visa.svg` + `amex.svg` are clean Figma SVGs, the other 4 (mastercard / discover / applepay / gpay) are PNGs from `get_screenshot`. See `PAYMENT_BRANDS` in `CartPageClient.jsx` for the per-icon `{ name, ext, w }` map.
- **Two GraphQL paths: server-side vs. client-side, never mix.**
  - **Server components** read through `src/lib/repairApi.js` → `repairQuery(operationName, variables, { revalidate })`. ISR-cached via `next.revalidate`, no auth header. Endpoint from `REPAIR_API_URL` env (server-side, no `NEXT_PUBLIC_` prefix), defaulting to `http://localhost:3000/repair/graphql`. Used by `HeaderShell.jsx` for `myAppListCategoriesTree`. Don't reach for this from a client component — the `next.revalidate` option is server-only and the helper is unaware of auth tokens.
  - **Client components** call `repairCall(operationName, variables, { isQuery })` from `src/lib/repairAuthedApi.js`. It pulls the access token from the Zustand store, sends `Authorization: Bearer <jwt>`, and on a 401 (or the synthetic 401 we attach to `"Un Authenticated User"` application failures — see `repairClientApi.js`) it calls `useRepairStore.getState().refreshAuth()` and retries once. Endpoint from `NEXT_PUBLIC_REPAIR_GRAPHQL_URL` env (client-side, must have the prefix). Don't import `repairApi.js` from a client component, and don't roll your own fetch — every authed call goes through `repairCall` so the 401-refresh-retry behaviour is uniform.
- **Client state: Zustand + AES-encrypted localStorage.** The store lives at `src/lib/useRepairStore.js` — five persisted slices (`authInfo`, `cartInfo`, `wishlistInfo`, `lastOrder`, `checkoutInfo` — the last is in-memory only) plus one transient (`sessionExpired`). Persistence uses `createJSONStorage(() => secureStorage)` with CryptoJS AES-256, key from `NEXT_PUBLIC_STORAGE_SECRET_KEY`. The key ships in the JS bundle — treat the encryption as obfuscation; real session security is server-side refresh-token rotation. The store is mounted via `<StoreProvider>` in the root layout, which `await`s `rehydrate()` client-side, calls `maybeProactiveRefresh()` to top up a near-expired token, then fires `syncCart()` + `syncWishlist()` if the rehydrated `authInfo.isLoggedIn` is true.
- **Explicit logout vs. forced session-expiry are different code paths — keep them split.** `clearAuth()` is the **explicit-logout** path (Sign Out button) — wipes EVERYTHING user-scoped (auth + cart + wishlist + lastOrder + checkout) because the next person on this device may be a different user. `handleSessionExpired()` is the **forced-sign-out** path (refresh failed, token reuse detected server-side, account deactivated, or 30-day refresh window finally elapsed) — wipes only the auth slice and **preserves cart/wishlist/lastOrder so the user signs back in and their basket is intact**, then sets `sessionExpired: true` so StoreProvider surfaces the toast and `?next=` redirects them back to where they were. **`refreshAuth()` on failure calls `handleSessionExpired`, NOT `clearAuth`** — if you ever revert this, the user loses their cart on every 30-day rotation timeout. Sign-out buttons should call `clearAuth()` and also call `myAppLogout` on the wire to revoke the server-side refresh token.
- **Refresh token rotation is single-flight-locked AND sliding.** Access tokens expire every 30 minutes (server-side `ACCESS_TOKEN_TTL = "30m"`); refresh tokens get a fresh 30-day window on every successful rotation (server slides `expires_at` to `now + 30d`), so any user who returns within 30 days of their last visit is never logged out. A module-level `_refreshInFlight` Promise in `useRepairStore.js` ensures concurrent callers share one refresh request; without the lock, a second in-flight refresh would reuse an already-rotated token and the server's rotation-detection logic would revoke the entire token family. Don't replicate refresh logic elsewhere — call `useRepairStore.getState().refreshAuth()` (or rely on `repairCall`, which calls it for you).
- **Proactive refresh hides the 30-min access TTL from the UX.** `useRepairStore.maybeProactiveRefresh()` peeks at the JWT `exp` claim (read-only — server is the only place that can trust the signature) and rotates the token only when fewer than `PROACTIVE_REFRESH_WINDOW_SEC` (5 min) remain. StoreProvider wires it to `visibilitychange` / `focus` / `online` and to post-rehydrate; **before a sensitive flow** (opening `/checkout/payment`, placing an order, etc.) call it manually so the user never sees a 401 → refresh → retry round-trip mid-action. Cheap to call — no-op when the token is still fresh.
- **Cross-tab auth sync via `BroadcastChannel("repair-auth")`.** Every `setAuthInfo` / `clearAuth` / `handleSessionExpired` posts a message; sibling tabs receive it through `initRepairStoreListener` and apply via `applyAuthInfoFromBroadcast` / `applySessionExpiredFromBroadcast` (the applier paths deliberately do NOT rebroadcast, preventing echo storms in 3+ tab setups). Without this, two open tabs each refresh independently with their own copy of the refresh token — the second one reuses an already-rotated token, the server's reuse-detection fires family revocation, and the user is silently logged out everywhere. The single-flight lock alone doesn't help here because tabs don't share JS scope; the channel is what keeps them coherent. **If you ever add a new auth-mutating action to the store, broadcast it.**
- **`?next=` round-trip + open-redirect rules are centralized in `@/lib/authRedirect`.** AuthGuard pushes `/sign-in?next=<path+search>` when the user isn't signed in; the session-expired flow does the same. All four sign-in paths (SignInForm, SignUpForm, GoogleSignInButton, CompleteProfileForm) call `postAuthDestination({ searchParams, role })` on success — honors `?next=` if it passes `isSameOriginPath` (single leading `/`, no `//evil.com`, no `/\\evil.com`), otherwise falls back to `homeForRole(role)` (admin → `/r3pr-console`, delivery → `/r3pr-dispatch`, accounting → `/r3pr-ledger`, customer → `/shop`). **Never reach for `router.push("/shop")` directly from an auth form** — go through `postAuthDestination` so the round-trip works AND the role-routing stays in one file. GoogleSignInButton stashes the validated `next` value alongside the `signupToken` in sessionStorage so it survives the `/complete-profile` hop. CompleteProfileForm re-validates with `isSameOriginPath` on the way out because the sessionStorage payload could have been tampered with.
- **Login flows are responsible for the initial sync AND for honoring `?next=`.** `StoreProvider` only triggers `syncCart()` + `syncWishlist()` on page mount + post-rehydrate. When the user actively signs in / signs up / completes OAuth, the handler must `setAuthInfo(data)` AND fire both syncs AND push to `postAuthDestination(...)` so the header badge populates without waiting for the next navigation and the user lands at the page that bounced them:
    ```js
    const data = await repairCall("myAppLogin", { email, password });  // Query
    const store = useRepairStore.getState();
    store.setAuthInfo(data);
    store.syncCart();
    store.syncWishlist();
    router.push(postAuthDestination({ searchParams, role: data?.user?.role }));
    ```
- **Component state stays in `useState`** for things that don't span pages (drawer open/close, filter form values, banner timeouts). `ShopPageClient.jsx` keeps its drawer / cart-banner state in `useState` and lifts filter changes into URL query params via `useRouter`/`useSearchParams` from `next/navigation` — keep that pattern. Don't reach for the Zustand store for ephemeral UI state. Don't add Redux / SWR / TanStack Query without discussing — the existing two-layer split (server reads via `repairApi`, client reads + mutations via `repairCall`, shared state in Zustand) covers the surface.
- **`"use client"` only when actually needed.** Server-component-first. Current client components: `SplashSection.jsx` (drives the fade and toggles `body.style.overflow`), `Header.jsx` (menu state + `usePathname` + hover dropdown), and `shared/Sidebar.jsx` (drilldown state + `Escape` key handling). Everything else — auth pages, footer, colorway sections — is a server component. Keep it that way: when a form needs `onSubmit` or state, isolate just the interactive piece into a client component rather than flipping the whole page. For data-fetching surfaces, prefer the `HeaderShell` pattern: a thin async server component that calls `repairApi` and forwards plain props to a client child.
- **Dynamic-route client-component escape hatch for new `[param]` routes.** Next 16 server components unwrap dynamic params with `const { id } = await params`. That works, but the very first cold load of a freshly-added dynamic route was hitting 404 even with the file present — restarting the dev server cleared it. When a new dynamic route needs to work reliably from the moment the file lands (e.g. `account/orders/[id]`), make the page a `"use client"` shell that reads `use(params)` and renders an inline "not found" fallback when the lookup fails, rather than calling `notFound()`. This avoids both the cache quirk and the heavier `notFound()` boundary for what's effectively presentational mock data. See `(customer)/account/orders/[id]/page.js` for the worked example.
- **Storefront content editor — preview parity.** `/r3pr-console/storefront` ships a Show preview / Hide preview toggle next to every section's Save bar. The preview components (`HeroPreview` / `ColorwayPreview` / `StatsPreview` / `BrowseTilesPreview` / `ProductSectionsPreview` / `CoachingPreview` / `FooterPreview`) are visual approximations of the real landing — black bg with the same gradient as `HeroSection`, the inline-rebuilt `GlassCtaPill` matching `GlassButton`'s inset shadow stack, alternating two-column colorway layout matching `ColorwaySection`, white footer with circular dark social bubbles matching the real `Footer.jsx`. **When you change the live `public/homePage/*` components (Hero/Colorway/Stats/Browse/Footer), mirror the change in the matching preview** so the "PREVIEW — UNSAVED" panel keeps showing an accurate demo before Save. Don't extract the previews into the real `homePage/*` components — they're deliberately self-contained inside `StorefrontManager.jsx` so an admin-only change can't accidentally break the customer landing.

## PWAs + Web Push

There are **two completely separate PWAs on this one origin**, split by scope + manifest + service worker:

| | Storefront | Admin console |
| --- | --- | --- |
| Manifest | `public/manifest.webmanifest` (scope `/`, dark theme, `icons/storefront-*`) | `public/manifest.admin.webmanifest` (scope `/r3pr-console/`, `icons/admin-*`) |
| Service worker | `public/sw.js` (scope `/`) | `public/sw-admin.js` (scope `/r3pr-console/`) |
| Registered by | `components/shared/StorefrontPwaRegister.jsx` (root layout; **skips** `/r3pr-console`, `/r3pr-ledger`, `/r3pr-dispatch`) | the `useAdminPush` hook (`lib/pwa.js`), mounted via admin `TopBar` |
| Manifest link | root `layout.js` `metadata.manifest` | `(admin)/layout.js` `metadata.manifest` (overrides root for `/r3pr-console`) |
| Push | **installable only** (no push) | **installable + Web Push** |

- **Separation** is by SW scope: a `/r3pr-console` page is controlled by the more-specific admin SW; everything else by the storefront SW. Separate manifests, icons, scopes, and (admin-only) push subscriptions. Icons were generated from `public/home/logo-re.png` into `public/icons/` (storefront = dark `#11191f`, admin = blue `#1d4ed8`, + a monochrome `badge-96.png` for the notification badge); regenerate with a `sharp` script if the logo changes.
- **Admin Web Push** (`lib/pwa.js`): `useAdminPush()` registers the admin SW (installability), and `enable()` — **called from a user gesture** (the "Enable push notifications" button in `NotificationPanel`'s `PushFooter`) — requests permission, subscribes with `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, and saves via `myAppAdminSavePushSubscription`. The server then pushes every admin notification (order/message/stock-alert/low-stock) to subscribed devices alongside the email (see Server `CLAUDE.md` migration 0028 + `push.ts`).
- **iOS reality:** iOS 16.4+ only allows Web Push for a PWA **installed to the home screen** (running standalone). `pushNeedsInstall()` detects iOS-not-installed and the `PushFooter` shows an "Add to Home Screen" instruction instead of a permission prompt (which would fail). No iOS/APNs-specific server code — standard VAPID Web Push reaches Apple's push service.
- **Testing limits:** an automation/headless browser hard-denies notifications, so the subscribe flow can only be exercised on a real browser with permission granted (and iOS push needs a physically installed PWA). The server push pipeline (VAPID load, fan-out, prune, `pushed_at` stamp) is testable independently.
- The service workers use `skipWaiting()` + `clients.claim()`; bump `SW_VERSION` in each to force-update clients.

## Shop drawers / overlays — animation + scroll conventions

The drawers and full-screen overlays under `customer/shop/` (FilterDrawer, AddToCartDrawer, SearchOverlay, ComingSoonOverlay) share a small animation system defined in `globals.css`. **Reuse it instead of inventing new keyframes.**

**Delayed-unmount hook.** Open/close animations only work if the element stays mounted through the exit. Each drawer file inlines its own `useDelayedUnmount(open, exitMs)` (15-line hook — duplicated, not shared) that holds `render=true` and toggles `data-state="open" | "closing"` on the aside + backdrop. CSS picks the enter / exit keyframe off the data-state, and the hook unmounts only after `exitMs`. The hook is now copied into **five** files (FilterDrawer, AddToCartDrawer, OrderFilterDrawer, WishlistFilterDrawer, admin Drawer) — the original "abstract on the fourth drawer" threshold has been crossed. Promoting to `customer/shared/useDelayedUnmount.js` (or a shared `BottomSheet` / `RightDrawer` primitive that bundles the hook + Escape handler + backdrop) is now reasonable next-cleanup work; until that lands, keep copying.

**CSS classes by surface type:**

| Class | Surface | Open animation | Exit animation |
| --- | --- | --- | --- |
| `.drawer-backdrop` | Backdrop scrim (rgba(17,25,31,0.50)) shared by all drawers | 280ms linear fade in | 280ms linear fade out |
| `.bottom-card` | Mobile bottom-anchored card — FilterDrawer mobile + AddToCartDrawer mobile + OrderFilterDrawer mobile + WishlistFilterDrawer mobile | 320ms linear slide up from `translateY(calc(100% + 24px))` (pure vertical) | 320ms linear slide back down |
| `.right-drawer` | Desktop right-side floating card — AddToCartDrawer desktop + FilterDrawer desktop + OrderFilterDrawer desktop + WishlistFilterDrawer desktop + admin Drawer | 300ms linear slide from `translateX(100%)` | 300ms linear slide back right |
| `.search-overlay` | SearchOverlay full-screen | 240ms linear fade in | 240ms linear fade out |

**All timings are `linear`** (deliberate — the previous spring/eased curves were rejected in favor of consistent mechanical motion). Don't reintroduce cubic-bezier for these.

**Mobile bottom-card centering.** `.bottom-card` is anchored at `left-0 right-0 mx-auto` (NOT `left-1/2 -translate-x-1/2`) because Tailwind v4's translate utilities use the `translate` CSS property while the keyframe uses `transform: translateY(...)` — combining them produces diagonal motion. Keep the centering off of transform.

**Reduced motion.** `globals.css` has a `@media (prefers-reduced-motion: reduce)` block that disables all four classes + `.splash-anim` + `.sidebar-view-anim`. Add any new animated drawer class to that block.

**Custom thin scrollbar.** `.drawer-scroll` gives a 4px transparent-track / `rgba(17,25,31,0.20)` thumb scrollbar (35% on hover) — Chromium via `::-webkit-scrollbar*`, Firefox via `scrollbar-width: thin` + `scrollbar-color`. Apply on any drawer/aside with `overflow-y-auto` to keep the design clean. AddToCartDrawer desktop uses it; FilterDrawer desktop uses it. Don't apply to the page itself.

**SearchOverlay placeholder typography.** `globals.css` includes `.search-overlay-input::placeholder` to set Zalando Sans Expanded Regular 12px @ `rgba(17,25,31,0.5)`. The input's resting text style is Bold 12px `#11191F` so typed content reads heavier than the placeholder, matching Figma 39:1953.

**ComingSoonOverlay sticky overlay.** When the blurred background grid exceeds viewport height (mobile, 8 cards in 2 cols = 4 rows), the centered icon+text uses `sticky top-1/2 -translate-y-1/2` so it stays visually centered as the user scrolls through the blur. On desktop where the grid fits the viewport, sticky behaves like regular centered absolute positioning. Don't replace with plain `absolute inset-0 justify-center` — that would push the overlay below the fold on tall mobile grids.

## Backend contract you are coding against

Every request from this app should go to `POST /repair/graphql`. The wire shape is the same `MyAppInput → MyAppResponse` envelope documented in the root CLAUDE.md, but in `repair` there is **no generic CRUD path** — each operation is a named resolver with its own auth + role check. The full inventory of named resolvers lives under `Server/servers/repair/src/graphql/resolvers/` (auth, catalog, adminCatalog, adminPricing, addresses, cart, orders, reports, admin). If a feature you are building has no matching resolver, the resolver needs to be added on the server side first; do not attempt to use a generic `myAppFindAll` / `myAppAddData` style call — those were removed in the May 2026 audit and a regression test fails fast if they reappear.

Auth header is `Authorization: Bearer <jwt>`. **Access tokens expire every 30 minutes** (server-side constant `ACCESS_TOKEN_TTL = "30m"` in `Server/servers/repair/src/graphql/resolvers/auth.ts`). Pair with the opaque refresh token (30-day TTL, single-use rotation — **sliding**: every successful rotation issues a fresh 30-day window, so an active user is never logged out and only genuinely abandoned sessions ever hit a hard expiry) returned alongside; exchange via `myAppRefreshToken` (a **Mutation**, not a Query — the server's `safeParse` expects camelCase `{ refreshToken }` as input).

**The client already handles all of this** — `repairCall` from `repairAuthedApi.js` auto-refreshes on 401 and retries; `useRepairStore.refreshAuth()` is single-flight-locked; `useRepairStore.maybeProactiveRefresh()` proactively rotates whenever the access token has under 5 minutes left (fired by StoreProvider on tab focus / network reconnect / post-rehydrate); `BroadcastChannel("repair-auth")` keeps every open tab's token pair in lock-step. When refresh ultimately fails (30-day window elapsed, token revoked, account deactivated, reuse detected), `handleSessionExpired()` clears the auth slice but **preserves cart + wishlist + lastOrder** and trips `sessionExpired` so StoreProvider shows a toast + redirects to `/sign-in?next=<here>`. Logout calls `myAppLogout` (single token) or `myAppLogoutAll` (all sessions for the user); both are Mutations and the client's `clearAuth()` should be called alongside so the access JWT is also dropped locally.

The `isAuth` middleware in the repair sub-server is **non-blocking** — an expired / missing / invalid token leaves `req.isAuth = false` and the request still reaches the resolver. Auth-gated resolvers then return `UNAUTH = fail("Un Authenticated User")` with **HTTP 200** + `blnRequestSuccessful: false`. The client's `graphqlFetch` recognises that exact string and synthesises `.status === 401` on the thrown error so the retry layer (`graphqlFetchWithRetry`, also used by `repairCall`) treats it the same as a real network 401. If a new server-side auth-failure code path is added later, either reuse the `UNAUTH` constant or update the message-match in `repairClientApi.js`.
