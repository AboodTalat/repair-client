# CLAUDE.md — `repair/src/lib/`

Per-file inventory for the `repair/` frontend's `src/lib/` directory (client/server GraphQL transports, the Zustand store + auth lifecycle, data hooks, pricing/cart helpers, nav shaping, and the remaining mock-data modules).

This is a **detail supplement** to the parent [`repair/CLAUDE.md`](../../CLAUDE.md) — read that first for the architecture, the two-GraphQL-paths rule, the auth/refresh model, conventions, the route map, and the backend contract. Keep both in sync: when you add or materially change a file here, update this file.

```
src/lib/
  repairApi.js            ← thin POST helper for /repair/graphql, **server-side only** — uses `next.revalidate` ISR caching (default 300s), no auth header. Used from server components (e.g. `HeaderShell.jsx`). Accepts a `tags` option for on-demand invalidation: the category-tree fetches in `storeNav.js` are tagged `CATEGORY_CACHE_TAG` ("repair-categories"), and the admin Categories page calls the `revalidateStorefrontCategories` server action (`categoryActions.js` → `revalidateTag`) after every category mutation so a newly added/edited category surfaces on the next storefront refresh instead of waiting out the 300s window. Without this the nav looked stale for up to 5 minutes after an admin change. **The same pattern covers products**: every product-derived storefront read in `shopCatalog.js` (grid / detail / related / facet options / category discount banner) is tagged `PRODUCT_CACHE_TAG` ("repair-products", exported from `shopCatalog.js`), and the admin Products page calls `revalidateStorefrontProducts` (`productActions.js`) after every mutation — product save, delete, hide-instead-of-delete, visibility toggle, inline category assign, and color/size CRUD. Without it an admin who edited a product and reloaded the storefront kept seeing the OLD copy for the rest of the 60s window **no matter how many times they refreshed** (the cache is server-side, so a browser reload never reaches past it). **When you add a new product-derived server read, tag it** — an untagged fetch silently reintroduces the stale-after-save bug.
  adminNav.js             ← **searchable index of admin DESTINATIONS** — every console page plus the 8 Settings cards. Pages are derived from `SideNav`'s **exported `SECTIONS`**, so a route added to the sidebar becomes searchable with no edit here; only the settings sub-destinations and the keyword synonyms are authored in this file. `searchDestinations(term)` is **pure + synchronous** and is called on every keystroke — deliberately NOT folded into `adminSearch.js`, whose `Promise.all` would make navigating to "Tax Rate" wait on three resolver round-trips. Ranking: exact label → label prefix → label substring → exact keyword → keyword prefix → keyword substring → section, capped at 6. Keywords carry synonyms (`vat`/`gst` → Tax Rate, `cod`/`cash on delivery` → Payment Methods, `fabric` → Materials, `customers` → Users & Roles, `cms`/`landing` → Storefront Content). **Scope is the admin console only** — `/r3pr-ledger` and `/r3pr-dispatch` are different role shells and are deliberately not indexed. Pinned by `adminNav.test.js` (18 cases), which is the only executable proof of the matcher since the dropdown itself is behind the admin login.
  adminSearch.js          ← **data layer for the admin TopBar global search**. `searchAdmin(term)` fans one term across `myAppListProducts({search,includeHidden})` + `myAppAdminListOrders({search})` + `myAppAdminListUsers({search})` in parallel, 5 per group, each leg independently `.catch`ed so one failing resolver can't blank the dropdown. Returns `{products, orders, customers, totals, empty}` and never throws. **Note the response keys differ**: products/orders return `items`, users returns `users` — mapping the wrong one yields a silently empty group. Order status runs through `rawToDisplayStatus`/`statusLabel` from `adminOrders.js` so a result never shows a raw enum. Also exports `MIN_SEARCH_LEN` (2) and `sectionHref(group, term)` → `/r3pr-console/<section>?q=<term>`; the three managers seed their search box from that param, so a click lands on a filtered list rather than a raw one. Min-length + the TopBar's 300ms debounce are cost control as much as UX — `myAppAdminListUsers` writes a `user.list` audit row on every call.
  productActions.js       ← `"use server"` module exporting `revalidateStorefrontProducts()` → `revalidateTag(PRODUCT_CACHE_TAG)`. Twin of `categoryActions.js`. Called best-effort (fire-and-forget, `.catch(() => {})`) from THREE admin pages: `admin/products/ProductManager.jsx` (`bustStorefrontProducts()`), `admin/taxonomies/TaxonomyManager.jsx` (`bustStorefrontFacets()` — materials are part of the same cached `fetchShopFacets()` bundle, so a material add/rename/delete must bust it too or the storefront filter drawer stays stale), and `admin/discounts/DiscountManager.jsx` (`bustStorefrontPricing()` — a discount changes the PRICE the cached product reads render, plus the `fetchCategoryDiscountBanner` read). **Any admin surface that mutates something inside `fetchShopFacets()` or the product reads must call this** — colors + sizes + price range (Products page), materials (Materials page). Must keep exporting ONLY async functions — that's a hard `"use server"` constraint, and it's why the tag constant lives in `shopCatalog.js` rather than here.
  repairClientApi.js      ← **client-side** GraphQL transport. Two exports: `graphqlFetch(operationName, variables, { token, isQuery })` (raw call, caller supplies the token) and `graphqlFetchWithRetry(operationName, variables, { getToken, refresh, isQuery })` (auto-refreshes once on a 401). Store-free by design so the dependency direction stays one-way (useRepairStore → repairClientApi); the refresh closure is passed in by the caller. Synthesises `.status === 401` on application-level `"Un Authenticated User"` failures (the repair `isAuth` middleware is non-blocking, so UNAUTH arrives as HTTP 200 with `blnRequestSuccessful: false` — without this synthesis the retry layer would never trigger). URL from `NEXT_PUBLIC_REPAIR_GRAPHQL_URL` env, falling back to `/repair/graphql`.
  repairAuthedApi.js      ← **high-level** client API. Exports a single function `repairCall(operationName, variables, { isQuery })` that wires `graphqlFetchWithRetry` to the Zustand store's `authInfo.token` + `refreshAuth()`. **Use this from every client component / event handler that needs an authed call** — it's the single API surface so 401-refresh-retry behaviour stays uniform across the app. Lives in its own file (not in `repairClientApi.js`) because it imports from `useRepairStore.js`, which already imports from `repairClientApi.js` — separating them avoids a circular import.
  useRepairStore.js       ← Zustand store for global client state. Six persisted slices + one transient: **authInfo** (JWT + refresh token + user — persisted, AES-encrypted), **cartInfo** (item count + last-synced timestamp — persisted; the logged-in badge count, reconciled from the server cart), **guestCart** (the signed-out visitor's local basket — persisted line items `{product_variant_id, quantity, product, color, size, image_url, line_total}` mirroring a `myAppGetCart` line; **INVARIANT: a logged-in user's guestCart is always empty** — `mergeGuestCartThenSync` clears it on login), **wishlistInfo** (product-id list + last-synced — persisted, for instant heart-icon state), **lastOrder** (most recent successfully-placed order — persisted so `/checkout/success` survives a refresh), **checkoutInfo** (in-progress checkout selections — NOT persisted, stale promo codes are bad UX), and **sessionExpired** (transient boolean — flips true when refresh fails or a sibling tab broadcasts session death; StoreProvider subscribes and triggers the toast + `?next=` round-trip). **Cart actions**: `addToCart(line)` (guest → upsert into guestCart; logged-in → `myAppAddToCart` via `graphqlFetchWithRetry` — NOT `repairCall`, to avoid the store→repairAuthedApi→store circular import — with optimistic count reverted on failure), `mergeGuestCartThenSync()` (call at the 4 login sites INSTEAD of `syncCart()`; seeds the badge from the guest sum to avoid a blink, pushes each guest line in parallel, clears guestCart unconditionally, then `syncCart`), `updateGuestCartItem`/`removeGuestCartItem`/`clearGuestCart`. **`selectCartCount` is DERIVED** per mode: `isLoggedIn ? cartInfo.itemCount : sumGuestQty(guestCart.items)` — never mirror the guest count into cartInfo. guestCart is wiped at 4 sites (initial, `clearAuth`, the broadcast `auth-cleared` receiver, `resetStore`) — keep those in sync. The `/cart` page consumes all this through the `useCart` hook (see below). Encrypted via CryptoJS AES-256 in localStorage under key `RepairStore_v1`; key from `NEXT_PUBLIC_STORAGE_SECRET_KEY` (obfuscation, not real secrecy — real security is server-side refresh-token rotation). `skipHydration: true` + manual `rehydrate()` from StoreProvider to avoid SSR mismatch. Module-level `_refreshInFlight` single-flight lock so concurrent 401s share one refresh Promise — without it, a second in-flight refresh would reuse an already-rotated token and the server would revoke the entire token family.

  **Auth lifecycle actions** (the important distinction): `setAuthInfo({ token, refresh_token, user })` after login/signup/Google/refresh (also broadcasts to sibling tabs); `clearAuth()` is the **explicit-logout** path — wipes EVERYTHING user-scoped (auth + cart + wishlist + lastOrder + checkout) because the next person on this device may be someone else; `handleSessionExpired()` is the **forced-sign-out** path (refresh failed, token reuse detected server-side, account deactivated, 30-day refresh window finally elapsed) — wipes only the auth slice and **preserves cart/wishlist/lastOrder so the user signs back in and finds their basket intact**, and sets `sessionExpired: true` so StoreProvider surfaces the toast and redirects with `?next=`. `refreshAuth()` returns the new token or null and now calls `handleSessionExpired` on failure (NOT `clearAuth`) — never reintroduce `clearAuth` here or the user loses their cart on every 30-day rotation timeout.

  **Proactive refresh**: `maybeProactiveRefresh()` peeks at the JWT `exp` claim (read-only — server is the only place that can trust the signature) and fires `refreshAuth` only when fewer than `PROACTIVE_REFRESH_WINDOW_SEC` (5 min) remain. Cheap to call. StoreProvider wires it to `visibilitychange` / `focus` / `online` and to the post-rehydrate sync; sensitive flows (checkout) can call it manually before opening a form to dodge mid-action 401s. **Keep `PROACTIVE_REFRESH_WINDOW_SEC` comfortably below the server's `ACCESS_TOKEN_TTL` (currently 30 min)** — if you ever cut the server TTL, also drop the window here.

  **Cross-tab auth sync via `BroadcastChannel("repair-auth")`**: every `setAuthInfo` / `clearAuth` / `handleSessionExpired` posts a message; sibling tabs receive it through `initRepairStoreListener` and apply via `applyAuthInfoFromBroadcast` / `applySessionExpiredFromBroadcast` (the applier paths deliberately DO NOT rebroadcast, which prevents echo storms in 3+ tab setups). Without this, tab A refreshing would leave tab B holding the old refresh token; B's next 401 would refresh too, reusing A's already-rotated token, and the server's reuse-detection would revoke the entire family — silently logging the user out everywhere. The single-flight lock alone is not enough because tabs don't share JS scope; the channel is what keeps them coherent.

  Cart/wishlist actions: `syncCart()` / `syncWishlist()` pull from server via `graphqlFetchWithRetry` so 30-minute access-token expiry is transparent; `incrementCartCount` / `decrementCartCount` (optimistic), `toggleWishlistItem(id)` (optimistic), `setLastPlacedOrder(order)` / `clearLastOrder()`, `applyPromoCode` / `clearPromoCode`, `setSelectedAddress` / `setShippingMethod` / `setSelectedPaymentMethod`, `clearCheckout()` (does NOT touch `lastOrder`), `resetStore()` (hard reset + clears encrypted localStorage), `clearSessionExpired()` (call after the UI has handled it), `getAccessTokenSecondsLeft()` (read-only helper). Selectors: `selectIsLoggedIn` / `selectUser` / `selectToken` / `selectCartCount` / `selectWishlistIds` / `selectCheckoutInfo` / `selectAppliedPromoCode` / `selectLastPlacedOrder` / `selectSessionExpired` / `selectWelcomeDiscountEligible` (cached `authInfo.user.welcome_discount_eligible` — used ONLY for the cosmetic landing banner; cart/checkout read the fresh flag from `myAppGetCart`). Also `markWelcomeDiscountUsed()` (flips the cached flag false after checkout consumes it — cosmetic, no broadcast; the server already flipped the authoritative flag and the cart self-corrects on its next fetch; ALSO stamps the device-level banner flag). **Device-level helpers** `markWelcomeBannerDismissedOnDevice()` / `isWelcomeBannerDismissedOnDevice()` / `subscribeWelcomeBannerDismissed(cb)` — a plain (UNencrypted, survives `clearAuth`) localStorage flag (`repair_welcome_used_v1`) recording that this device has **taken** the first-order welcome offer. It is set at **redemption** (`markWelcomeDiscountUsed`) AND at **every signup** (all 4 signup call sites call `markWelcomeBannerDismissedOnDevice()` on success). Two consumers: (1) the landing's guest "GET 10% OFF" banner stays hidden afterwards; (2) **every signup call site reads it via `isWelcomeBannerDismissedOnDevice()` and sends it to the server as `welcomeClaimedOnDevice`** — `myAppSignUp` / `myAppCompleteGoogleSignUp` then create the account WITHOUT `welcome_discount_eligible`, blocking the "log out → sign up again for another 10%" abuse. Server-side the signal can only DOWNGRADE eligibility (see Server `CLAUDE.md` migration-0026 note). **It's a deterrent, not enforcement** — incognito / cleared storage / another browser reset the flag; the real per-user gate is server-side `users.welcome_discount_eligible`. The mark fn dispatches a `repair-welcome-dismissed` event so the banner (which reads via `useSyncExternalStore`) hides without a reload. Also exports `initRepairStoreListener()` which watches for cross-tab + same-tab `localStorage.removeItem` AND attaches the BroadcastChannel receiver (one listener, two responsibilities). **Login flows must call `setAuthInfo(data)` AND `syncCart()` + `syncWishlist()`** so badge counts populate immediately — StoreProvider only fires that pair on page mount + post-rehydrate.
  authRedirect.js         ← single source of truth for the `?next=` round-trip used by every auth-redirect flow (AuthGuard → /sign-in, session-expired toast → /sign-in, sign-in / sign-up / Google / complete-profile → original destination, guest cart CTA → /sign-in?next=/cart, sign-in ↔ sign-up cross-links). Exports `homeForRole(role)` (admin → /r3pr-console, delivery → /r3pr-dispatch, accounting → /r3pr-ledger, customer → /shop — the canonical post-auth landing per role), `isSameOriginPath(p)` (open-redirect guard: rejects empty strings, non-`/`-leading paths, `//evil.com`-style protocol-relative URLs, and `/\\evil.com`-style IE-quirk URLs), `readNextParam(searchParams)` (returns the validated `?next` value or null), `buildSignInRedirect(here)` (encodes the path into `/sign-in?next=…`), and `postAuthDestination({ searchParams, role })` (the success-side resolver — honors `?next=` if safe, falls back to the role's home). **Seven places use this; if you add another auth-redirect flow, import from here rather than re-implementing the validation** — a bypass introduced in one form would otherwise widen the open-redirect surface for the others.
  shopCatalog.js          ← **server-side** storefront catalogue reads (via `repairApi`/`repairQuery`). `fetchShopProducts({ majorId, subId, colorIds, sizeIds, materialIds, subCategoryIds, minPrice, maxPrice, limit, offset })` → `{ items, total }` (cards via `mapListItemToCard`; `revalidate:0`), `fetchShopFacets()` → `{ colors:[{id,name,hex}], sizes:[{id,name}], materials:[{id,name}], priceRange:{min,max}|null }` (the filter-drawer options + live price bounds; `cache()` + `revalidate:300`), `fetchProductDetail(slug)` (product page; React `cache()`d), and **`fetchCategoryDiscountBanner({ majorId, subId })`** → the active admin-flagged discount banner payload for the viewed category (or null) via `myAppGetCategoryDiscountBanner` (short `STOREFRONT_REVALIDATE` window; the shop page fetches it in parallel with the product grid and passes it to `ShopPageClient` → `CategoryDiscountBanner`). The shop page maps the drawer's human-readable filter values → backend ids at the page boundary, so the URL + drawer keep speaking display values.
  storefrontContent.js    ← **server-side** read of the landing CMS. `fetchStorefrontContent()` → `repairQuery("myAppGetStorefrontContent", {}, { revalidate: 0 })` (UNCACHED so a refresh always shows the admin's latest save; the landing route is therefore dynamic). Returns the section map + top-level keys (`hero` / `colorways_intro` / `colorways` / `crafted_to_last` / `stats` / `browse_tiles` / `product_sections` / `coaching` / `footer`); any failure degrades to `{}` so the landing never breaks. Consumed by `app/page.js` (landing), `products/[slug]/page.js`, and `checkout/success/page.js`.
  storefrontDefaults.js   ← **the storefront CMS parity anchor.** Exports the canonical current-design defaults per section (`HERO_DEFAULT`, `COLORWAYS_INTRO_DEFAULT`, `COLORWAYS_DEFAULT`, `CRAFTED_TO_LAST_DEFAULT`, `STATS_DEFAULT`, `BROWSE_TILES_DEFAULT`, `FOOTER_DEFAULT`, `PRODUCT_SECTIONS_DEFAULT`, `COACHING_DEFAULT`, + the `STOREFRONT_DEFAULTS` map). Imported by BOTH the live landing components (render-time fallback) AND the admin `StorefrontManager` (first-open seed) so they can never drift — an empty CMS renders byte-identical to today. Values mirror the LIVE markup; **do NOT reconcile against `mockAdmin.STOREFRONT_*`, which diverges** (different hero copy/image, stats, browse tiles, coaching). When you change a live `homePage/*` (or product/coaching) component's copy, update the matching default here too.
  cartTotals.js           ← pure `computeCartTotals(items, settings, subtotalOverride, promoDiscount, shippingMethodKey = "standard", welcomeDiscountEligible = false)` — **6th arg drives the first-order welcome discount**: `welcomeDiscount = welcomeDiscountEligible ? min(10% of subtotal, subtotal) : 0` (mirrors `myAppCheckout`). **The welcome discount and a promo code are MUTUALLY EXCLUSIVE** — when eligible, the promo is forced to 0 (`discount = 0`) so the two never stack and the preview matches checkout (which ignores the promo while eligible). Returned in the totals object as `welcomeDiscount`. Exports `WELCOME_DISCOUNT_PCT` (mirror of the server constant — keep in lockstep). Eligibility is NEVER assumed client-side; it comes from `myAppGetCart.welcome_discount_eligible` (server-authoritative) via useCart. — MIRRORS `myAppCheckout`'s money math (Server `orders.ts` ~445-476): `afterPromo = max(0, subtotal - promoDiscount)`, shipping per the **selected method** (`pickup` → 0, `express` → `express_shipping_fee`, `standard` → fee waived when `afterPromo >= threshold`), `tax = inclusive ? 0 : afterPromo * rate/100` (subtotal-only base — shipping is never taxed; the `applies_to_shipping` toggle was removed). **`inclusive` is no longer admin-editable** (Aug 2026) — the Settings toggle was removed and the store is tax-exclusive; the branch stays because the column is still honoured, but only a direct DB change can flip it, total = afterPromo + shipping + tax. The returned object now also exposes `afterPromo`. Also exports `shippingForMethod(shipSettings, key, afterPromo)` and `buildDeliveryMethods(settings, afterPromo)` → `[{ id:key, label:name, description:eta, price }]` for ENABLED methods only — gated solely by each `shipping_methods` row, matching `myAppCheckout`. The old express double-gate on `shipping.express_shipping_enabled` was removed Aug 2026 (two switches for one method meant Express could read "Shown" and still be invisible). That flag is now **retired from the API entirely** — `myAppGetCommerceSettings` no longer returns it and `myAppAdminUpdateShippingSettings` **refuses** a write containing it (naming the Shipping Methods card instead). The DB column survives only so no migration was needed; nothing reads it. `settings` is the `myAppGetCommerceSettings` payload (null → no charges, `[]` methods). `promoDiscount` is the SERVER-computed `discount_amount` from `myAppValidatePromoCode` (0 = no promo) — never recompute the percent/fixed/cap math here. Used by `useCart` (so the cart estimate matches checkout) and the `/checkout` details page (method-aware).
  useCart.js              ← **client** data layer for the `/cart` AND `/checkout` details pages, branching on auth. Signature `useCart({ shippingMethodKey } = {})` (default `"standard"`; `/cart` calls it argless, checkout passes the selected method so totals react). Guest → reads/writes the store's `guestCart` slice (sync). Logged-in → `myAppGetCart` on mount + optimistic `myAppUpdateCartItem`/`myAppRemoveCartItem` (qty mutation **debounced 350ms per line** — the resolver writes an ABSOLUTE quantity, so rapid +/+/+ would otherwise race; server subtotal nudged optimistically, silent refetch reconciles, then `syncCart`). Both modes project to ONE display shape `{ id, variantId, name, variantLabel, image, price, qty, maxQty }`. **Hydration-gated** (`persist.hasHydrated()`) and exposes `loading` so the cart never flashes "empty" during the fetch / guest→login-merge window. Returns `{ items, loading, error, isGuest, totals, updateQty, removeItem, clearError, appliedPromo, applyPromo, clearPromo, promoError, clearPromoError }`. **First-order welcome discount**: captures `welcome_discount_eligible` from each `myAppGetCart` (state `serverWelcomeEligible`, refreshed every fetch — server-authoritative) and passes it (only when logged-in) as `computeCartTotals`'s 6th arg, so the cart/checkout preview shows the 10% line that checkout will actually charge. **`applyPromo` short-circuits when `serverWelcomeEligible`** (can't combine — same message the server returns) and the promo re-validate effect clears any stale applied promo + skips while eligible.
  useAddresses.js         ← **client** hook for the logged-in user's saved shipping addresses (used by `/checkout`). Branches like `useCart`: logged-in → `myAppGetMyAddresses` on mount, maps the backend shape to a display shape `{ id, label, kind (derived from label), full_name, phone, line (via buildAddressLine), isDefault, ...structured }`, and exposes `saveAddress(payload, { id? })` → `myAppAddAddress`/`myAppUpdateAddress` then refetch; guest → empty list (the guest's single address is held in the checkout component until registration). Hydration-gated.
  authValidation.js       ← pure, store-free validators reused by the `/checkout` guest-registration form: `validateEmail`, `validatePassword` (≥8), `normalizePhone(localDigits, dialCode, iso2)` → `{ phone, error }` (strips trunk-0 + duplicated dial code, length-checks via `phoneLengthFor`). Mirrors `SignUpForm`'s inline rules (SignUpForm itself still inlines its own copy — adopting these there is a safe follow-up).
  adminDates.js           ← **LOCAL calendar-date helpers** for every admin/accountant date filter the client COMPUTES (as opposed to one typed into a date input). Exports `toLocalISODate(d)` / `todayISO()` / `daysAgoISO(n)` / `startOfYearISO()` / `formatISODate(value)`. **The bug it replaces:** `adminDashboard.js`, `ReportsView.jsx` and `FinanceOverview.jsx` each carried a verbatim `new Date().toISOString().slice(0, 10)`, which yields the **UTC** calendar date — but this deployment's MySQL session runs on the machine's timezone (Asia/Amman, UTC+3; verified via `SELECT NOW()`), so `DATE_FORMAT(created_at, '%Y-%m-%d')` buckets on AMMAN dates. For most of the day the two agree; between **00:00 and 03:00 local** they don't, so `endDate` landed on yesterday 23:59:59 and every order since local midnight fell outside the window — the dashboard's Total Sales KPI, the revenue donut, the last point of the 7-day chart and every 7D/30D/90D/YTD preset silently dropped the current day. No error, just quietly low numbers in the small hours. **Only for client-computed dates:** a value from `<input type="date">` is already a local calendar date, and `priorRange` in `adminReports.js` is unaffected (it parses and re-formats through UTC symmetrically, so it only ever shifts a date string by whole days). **Known remaining UTC slices, deliberately NOT changed:** `isoToDateInput` in `DiscountManager.jsx` + `PromoManager.jsx` — both carry a comment saying UTC is the chosen convention for round-tripping a stored timestamp into a date input, so flipping them needs the save path checked first; and the CSV *filename* stamps in `DashboardView`/`SubscribersManager`, which are cosmetic. **CORRECTION (Aug 2026):** this file's original rationale was wrong — it claimed MySQL bucketed on Amman dates, "verified via `SELECT NOW()`", but that had been measured over a BARE mysql2 connection, which inherits the host zone. Through the app the session is pinned `+00:00`, so buckets were always UTC and a UTC-derived `todayISO` never dropped the current day. The real defect was that the RESOLVERS read these local strings as UTC instants: an order at 01:00 Amman was charted a day early and vanished when it fell on a range's first day. That half is fixed server-side (`REPORT_TZ_SQL` in `Server/servers/repair/src/graphql/helpers.ts`), which is what makes local calendar dates the correct output here. If `REPORT_TIMEZONE` ever changes, these helpers must follow.
  imageSpec.js            ← **the product-photo dimension contract**, enforced at upload time by the admin Products → Media tab. Exports `PRODUCT_IMAGE_WIDTH`/`_HEIGHT` (998 × 1498), `PRODUCT_IMAGE_RATIO`, `PRODUCT_IMAGE_RATIO_TOLERANCE` (±3%), `PRODUCT_IMAGE_SPEC_LABEL`, `readImageDimensions(file)`, `validateProductImage(file)` → `{ok,name,width,height,reason}` (never throws), `validateProductImages(files)` → `{accepted, rejected}`, and `describeRejections(rejected)`. **Why it exists:** every storefront product-photo slot is a fixed 2:3 portrait with `object-cover` (ProductCard 176×264 / 326×489, AddToCartDrawer 326×489, product page 361×541 / 508×761). `object-cover` never distorts — it CROPS — so an off-ratio upload silently eats the top and bottom of the picture on every card, and an undersized one is upscaled in the 508×761 hero (1016×1522 at 2× DPR) and reads as a blurry product photo. Neither raises an error anywhere, which is why the gate has to sit at the upload boundary. **The minimum checks WIDTH only** — a mathematically exact 2:3 image 998px wide is 998 × **1497**, so a strict `height >= 1498` would reject the exact shape the spec asks for; the ratio check already pins the height. No upper bound (`next/image` downscales; the 4 MB UploadThing cap is the ceiling). **Client-side only, and deliberately so** — this is a quality gate for trusted admins, not a security boundary, so don't mirror it into the resolver. Scope is product photos only; category tiles (`categoryImage`) and the storefront CMS use different ratios and are not gated.
  mockShop.js             ← in-process mock catalogue for /shop. Exports MAJOR_CATEGORIES (Discover All / Just Dropped / Women / Men / Sale), ALL_PRODUCTS + SALE_PRODUCTS (with `salePrice` and optional `labels: string[]` — `["Best Seller", "Most Popular", "New Arrival", "Limited", "Low Stock"]`), `getCategory(slug)`, `listProducts({ category, sub, filters })`, `ACTIVE_FILTER_COUNT(filters)`, and FILTER_OPTIONS (numericSizes 36-48 / sizes S-XXL / 10 colors / 5 materials / `types`). **`FILTER_OPTIONS.types` is derived at module load from `MAJOR_CATEGORIES.subs`** (deduped sub-category names) — sub-categories ARE the "type" facet on the storefront. Don't reintroduce a hardcoded `types` array; if you need to surface more types, add sub-categories on `MAJOR_CATEGORIES` (or via the Categories admin page once wired). Swap to a repairQuery call when the backend exposes a storefront list resolver.
  orders.js               ← order DISPLAY helpers for the customer `/account/orders` list AND per-order `/account/orders/[id]` tracking page (was `mockOrders.js`; **the mock ORDERS array + findOrder are gone — both surfaces are wired to the backend now**).
```
