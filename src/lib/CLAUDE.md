# CLAUDE.md — `repair/src/lib/`

Per-file inventory for the `repair/` frontend's `src/lib/` directory (client/server GraphQL transports, the Zustand store + auth lifecycle, data hooks, pricing/cart helpers, nav shaping, and the remaining mock-data modules).

This is a **detail supplement** to the parent [`repair/CLAUDE.md`](../../CLAUDE.md) — read that first for the architecture, the two-GraphQL-paths rule, the auth/refresh model, conventions, the route map, and the backend contract. Keep both in sync: when you add or materially change a file here, update this file.

```
src/lib/
  repairApi.js            ← thin POST helper for /repair/graphql, **server-side only** — uses `next.revalidate` ISR caching (default 300s), no auth header. Used from server components (e.g. `HeaderShell.jsx`). Accepts a `tags` option for on-demand invalidation: the category-tree fetches in `storeNav.js` are tagged `CATEGORY_CACHE_TAG` ("repair-categories"), and the admin Categories page calls the `revalidateStorefrontCategories` server action (`categoryActions.js` → `revalidateTag`) after every category mutation so a newly added/edited category surfaces on the next storefront refresh instead of waiting out the 300s window. Without this the nav looked stale for up to 5 minutes after an admin change.
  repairClientApi.js      ← **client-side** GraphQL transport. Two exports: `graphqlFetch(operationName, variables, { token, isQuery })` (raw call, caller supplies the token) and `graphqlFetchWithRetry(operationName, variables, { getToken, refresh, isQuery })` (auto-refreshes once on a 401). Store-free by design so the dependency direction stays one-way (useRepairStore → repairClientApi); the refresh closure is passed in by the caller. Synthesises `.status === 401` on application-level `"Un Authenticated User"` failures (the repair `isAuth` middleware is non-blocking, so UNAUTH arrives as HTTP 200 with `blnRequestSuccessful: false` — without this synthesis the retry layer would never trigger). URL from `NEXT_PUBLIC_REPAIR_GRAPHQL_URL` env, falling back to `/repair/graphql`.
  repairAuthedApi.js      ← **high-level** client API. Exports a single function `repairCall(operationName, variables, { isQuery })` that wires `graphqlFetchWithRetry` to the Zustand store's `authInfo.token` + `refreshAuth()`. **Use this from every client component / event handler that needs an authed call** — it's the single API surface so 401-refresh-retry behaviour stays uniform across the app. Lives in its own file (not in `repairClientApi.js`) because it imports from `useRepairStore.js`, which already imports from `repairClientApi.js` — separating them avoids a circular import.
  useRepairStore.js       ← Zustand store for global client state. Six persisted slices + one transient: **authInfo** (JWT + refresh token + user — persisted, AES-encrypted), **cartInfo** (item count + last-synced timestamp — persisted; the logged-in badge count, reconciled from the server cart), **guestCart** (the signed-out visitor's local basket — persisted line items `{product_variant_id, quantity, product, color, size, image_url, line_total}` mirroring a `myAppGetCart` line; **INVARIANT: a logged-in user's guestCart is always empty** — `mergeGuestCartThenSync` clears it on login), **wishlistInfo** (product-id list + last-synced — persisted, for instant heart-icon state), **lastOrder** (most recent successfully-placed order — persisted so `/checkout/success` survives a refresh), **checkoutInfo** (in-progress checkout selections — NOT persisted, stale promo codes are bad UX), and **sessionExpired** (transient boolean — flips true when refresh fails or a sibling tab broadcasts session death; StoreProvider subscribes and triggers the toast + `?next=` round-trip). **Cart actions**: `addToCart(line)` (guest → upsert into guestCart; logged-in → `myAppAddToCart` via `graphqlFetchWithRetry` — NOT `repairCall`, to avoid the store→repairAuthedApi→store circular import — with optimistic count reverted on failure), `mergeGuestCartThenSync()` (call at the 4 login sites INSTEAD of `syncCart()`; seeds the badge from the guest sum to avoid a blink, pushes each guest line in parallel, clears guestCart unconditionally, then `syncCart`), `updateGuestCartItem`/`removeGuestCartItem`/`clearGuestCart`. **`selectCartCount` is DERIVED** per mode: `isLoggedIn ? cartInfo.itemCount : sumGuestQty(guestCart.items)` — never mirror the guest count into cartInfo. guestCart is wiped at 4 sites (initial, `clearAuth`, the broadcast `auth-cleared` receiver, `resetStore`) — keep those in sync. The `/cart` page consumes all this through the `useCart` hook (see below). Encrypted via CryptoJS AES-256 in localStorage under key `RepairStore_v1`; key from `NEXT_PUBLIC_STORAGE_SECRET_KEY` (obfuscation, not real secrecy — real security is server-side refresh-token rotation). `skipHydration: true` + manual `rehydrate()` from StoreProvider to avoid SSR mismatch. Module-level `_refreshInFlight` single-flight lock so concurrent 401s share one refresh Promise — without it, a second in-flight refresh would reuse an already-rotated token and the server would revoke the entire token family.

  **Auth lifecycle actions** (the important distinction): `setAuthInfo({ token, refresh_token, user })` after login/signup/Google/refresh (also broadcasts to sibling tabs); `clearAuth()` is the **explicit-logout** path — wipes EVERYTHING user-scoped (auth + cart + wishlist + lastOrder + checkout) because the next person on this device may be someone else; `handleSessionExpired()` is the **forced-sign-out** path (refresh failed, token reuse detected server-side, account deactivated, 30-day refresh window finally elapsed) — wipes only the auth slice and **preserves cart/wishlist/lastOrder so the user signs back in and finds their basket intact**, and sets `sessionExpired: true` so StoreProvider surfaces the toast and redirects with `?next=`. `refreshAuth()` returns the new token or null and now calls `handleSessionExpired` on failure (NOT `clearAuth`) — never reintroduce `clearAuth` here or the user loses their cart on every 30-day rotation timeout.

  **Proactive refresh**: `maybeProactiveRefresh()` peeks at the JWT `exp` claim (read-only — server is the only place that can trust the signature) and fires `refreshAuth` only when fewer than `PROACTIVE_REFRESH_WINDOW_SEC` (5 min) remain. Cheap to call. StoreProvider wires it to `visibilitychange` / `focus` / `online` and to the post-rehydrate sync; sensitive flows (checkout) can call it manually before opening a form to dodge mid-action 401s. **Keep `PROACTIVE_REFRESH_WINDOW_SEC` comfortably below the server's `ACCESS_TOKEN_TTL` (currently 30 min)** — if you ever cut the server TTL, also drop the window here.

  **Cross-tab auth sync via `BroadcastChannel("repair-auth")`**: every `setAuthInfo` / `clearAuth` / `handleSessionExpired` posts a message; sibling tabs receive it through `initRepairStoreListener` and apply via `applyAuthInfoFromBroadcast` / `applySessionExpiredFromBroadcast` (the applier paths deliberately DO NOT rebroadcast, which prevents echo storms in 3+ tab setups). Without this, tab A refreshing would leave tab B holding the old refresh token; B's next 401 would refresh too, reusing A's already-rotated token, and the server's reuse-detection would revoke the entire family — silently logging the user out everywhere. The single-flight lock alone is not enough because tabs don't share JS scope; the channel is what keeps them coherent.

  Cart/wishlist actions: `syncCart()` / `syncWishlist()` pull from server via `graphqlFetchWithRetry` so 30-minute access-token expiry is transparent; `incrementCartCount` / `decrementCartCount` (optimistic), `toggleWishlistItem(id)` (optimistic), `setLastPlacedOrder(order)` / `clearLastOrder()`, `applyPromoCode` / `clearPromoCode`, `setSelectedAddress` / `setShippingMethod` / `setSelectedPaymentMethod`, `clearCheckout()` (does NOT touch `lastOrder`), `resetStore()` (hard reset + clears encrypted localStorage), `clearSessionExpired()` (call after the UI has handled it), `getAccessTokenSecondsLeft()` (read-only helper). Selectors: `selectIsLoggedIn` / `selectUser` / `selectToken` / `selectCartCount` / `selectWishlistIds` / `selectCheckoutInfo` / `selectAppliedPromoCode` / `selectLastPlacedOrder` / `selectSessionExpired`. Also exports `initRepairStoreListener()` which watches for cross-tab + same-tab `localStorage.removeItem` AND attaches the BroadcastChannel receiver (one listener, two responsibilities). **Login flows must call `setAuthInfo(data)` AND `syncCart()` + `syncWishlist()`** so badge counts populate immediately — StoreProvider only fires that pair on page mount + post-rehydrate.
  authRedirect.js         ← single source of truth for the `?next=` round-trip used by every auth-redirect flow (AuthGuard → /sign-in, session-expired toast → /sign-in, sign-in / sign-up / Google / complete-profile → original destination, guest cart CTA → /sign-in?next=/cart, sign-in ↔ sign-up cross-links). Exports `homeForRole(role)` (admin → /r3pr-console, delivery → /r3pr-dispatch, accounting → /r3pr-ledger, customer → /shop — the canonical post-auth landing per role), `isSameOriginPath(p)` (open-redirect guard: rejects empty strings, non-`/`-leading paths, `//evil.com`-style protocol-relative URLs, and `/\\evil.com`-style IE-quirk URLs), `readNextParam(searchParams)` (returns the validated `?next` value or null), `buildSignInRedirect(here)` (encodes the path into `/sign-in?next=…`), and `postAuthDestination({ searchParams, role })` (the success-side resolver — honors `?next=` if safe, falls back to the role's home). **Seven places use this; if you add another auth-redirect flow, import from here rather than re-implementing the validation** — a bypass introduced in one form would otherwise widen the open-redirect surface for the others.
  shopCatalog.js          ← **server-side** storefront catalogue reads (via `repairApi`/`repairQuery`). `fetchShopProducts({ majorId, subId, colorIds, sizeIds, materialIds, subCategoryIds, minPrice, maxPrice, limit, offset })` → `{ items, total }` (cards via `mapListItemToCard`; `revalidate:0`), `fetchShopFacets()` → `{ colors:[{id,name,hex}], sizes:[{id,name}], materials:[{id,name}], priceRange:{min,max}|null }` (the filter-drawer options + live price bounds; `cache()` + `revalidate:300`), `fetchProductDetail(slug)` (product page; React `cache()`d). The shop page maps the drawer's human-readable filter values → backend ids at the page boundary, so the URL + drawer keep speaking display values.
  cartTotals.js           ← pure `computeCartTotals(items, settings, subtotalOverride, promoDiscount, shippingMethodKey = "standard")` — MIRRORS `myAppCheckout`'s money math (Server `orders.ts` ~445-476): `afterPromo = max(0, subtotal - promoDiscount)`, shipping per the **selected method** (`pickup` → 0, `express` → `express_shipping_fee`, `standard` → fee waived when `afterPromo >= threshold`), `tax = inclusive ? 0 : afterPromo * rate/100` (subtotal-only base — shipping is never taxed; the `applies_to_shipping` toggle was removed), total = afterPromo + shipping + tax. The returned object now also exposes `afterPromo`. Also exports `shippingForMethod(shipSettings, key, afterPromo)` and `buildDeliveryMethods(settings, afterPromo)` → `[{ id:key, label:name, description:eta, price }]` for ENABLED methods only (express **double-gated** on `shipping.express_shipping_enabled`, else `myAppCheckout` rejects it). `settings` is the `myAppGetCommerceSettings` payload (null → no charges, `[]` methods). `promoDiscount` is the SERVER-computed `discount_amount` from `myAppValidatePromoCode` (0 = no promo) — never recompute the percent/fixed/cap math here. Used by `useCart` (so the cart estimate matches checkout) and the `/checkout` details page (method-aware).
  useCart.js              ← **client** data layer for the `/cart` AND `/checkout` details pages, branching on auth. Signature `useCart({ shippingMethodKey } = {})` (default `"standard"`; `/cart` calls it argless, checkout passes the selected method so totals react). Guest → reads/writes the store's `guestCart` slice (sync). Logged-in → `myAppGetCart` on mount + optimistic `myAppUpdateCartItem`/`myAppRemoveCartItem` (qty mutation **debounced 350ms per line** — the resolver writes an ABSOLUTE quantity, so rapid +/+/+ would otherwise race; server subtotal nudged optimistically, silent refetch reconciles, then `syncCart`). Both modes project to ONE display shape `{ id, variantId, name, variantLabel, image, price, qty, maxQty }`. **Hydration-gated** (`persist.hasHydrated()`) and exposes `loading` so the cart never flashes "empty" during the fetch / guest→login-merge window. Returns `{ items, loading, error, isGuest, totals, updateQty, removeItem, clearError, appliedPromo, applyPromo, clearPromo, promoError, clearPromoError }`.
  useAddresses.js         ← **client** hook for the logged-in user's saved shipping addresses (used by `/checkout`). Branches like `useCart`: logged-in → `myAppGetMyAddresses` on mount, maps the backend shape to a display shape `{ id, label, kind (derived from label), full_name, phone, line (via buildAddressLine), isDefault, ...structured }`, and exposes `saveAddress(payload, { id? })` → `myAppAddAddress`/`myAppUpdateAddress` then refetch; guest → empty list (the guest's single address is held in the checkout component until registration). Hydration-gated.
  authValidation.js       ← pure, store-free validators reused by the `/checkout` guest-registration form: `validateEmail`, `validatePassword` (≥8), `normalizePhone(localDigits, dialCode, iso2)` → `{ phone, error }` (strips trunk-0 + duplicated dial code, length-checks via `phoneLengthFor`). Mirrors `SignUpForm`'s inline rules (SignUpForm itself still inlines its own copy — adopting these there is a safe follow-up).
  mockShop.js             ← in-process mock catalogue for /shop. Exports MAJOR_CATEGORIES (Discover All / Just Dropped / Women / Men / Sale), ALL_PRODUCTS + SALE_PRODUCTS (with `salePrice` and optional `labels: string[]` — `["Best Seller", "Most Popular", "New Arrival", "Limited", "Low Stock"]`), `getCategory(slug)`, `listProducts({ category, sub, filters })`, `ACTIVE_FILTER_COUNT(filters)`, and FILTER_OPTIONS (numericSizes 36-48 / sizes S-XXL / 10 colors / 5 materials / `types`). **`FILTER_OPTIONS.types` is derived at module load from `MAJOR_CATEGORIES.subs`** (deduped sub-category names) — sub-categories ARE the "type" facet on the storefront. Don't reintroduce a hardcoded `types` array; if you need to surface more types, add sub-categories on `MAJOR_CATEGORIES` (or via the Categories admin page once wired). Swap to a repairQuery call when the backend exposes a storefront list resolver.
  orders.js               ← order DISPLAY helpers for the customer `/account/orders` list AND per-order `/account/orders/[id]` tracking page (was `mockOrders.js`; **the mock ORDERS array + findOrder are gone — both surfaces are wired to the backend now**). Keys mirror the REAL `orders.status` enum (`pending` / `processing` / `dispatched` / `out_for_delivery` / `delivered` / `failed_delivery` / `cancelled` / `returned`) — every value maps to a badge bucket, a filter chip, and a pipeline step with no silent fall-through. Exports `badgeFor(status)` (**one badge per real status** — `Pending` / `Processing` / `Dispatched` / `Out for Delivery` / `Delivered` / `Delivery failed` / `Cancelled` / `Returned`; the in-transit states are NO LONGER collapsed into a single "On the way" pill — a `processing` order must not read as in-transit — and the `default` is a neutral `Unknown`, never a silent "on the way" fall-through), `isInFlight(status)` (drives the Track CTA — still true for all four in-transit states), `ORDER_STATUS_OPTIONS` (5 multi-select chips — `delivered` / `on-the-way` / `failed` / `cancelled` / `returned`; each carries `rawStatuses`), `ORDER_DATE_RANGES` (single-select: `all` / `30d` / `6m` / `year`), `filterOrders(orders, { statuses, dateRange })` (client-side, on display rows carrying raw `status` + ISO `purchasedAt`), `ACTIVE_ORDER_FILTER_COUNT(filters)`, **`TRACKING_PIPELINE`** (4 steps: processing → dispatched → out_for_delivery → delivered) + **`trackingProgress(status)`** → `{ stepIndex, terminal: "cancelled"|"returned"|"failed_delivery"|null }`, `formatOrderDate(iso)` ("21st March 2026"), and **`mapServerOrderToCard(o)`** (maps a `myAppGetMyOrders` row — raw order + `item_count` + `preview_item` — into the card shape). Re-exports `formatJOD`.
  mockWishlist.js         ← in-process mock data for the customer `/account/wishlist` page. Exports WISHLIST (4 sample rows; each carries product display info + a swatch palette + a `type` matching FILTER_OPTIONS.types from mockShop), `WISHLIST_TYPE_OPTIONS` (multi-select pills sourced from `FILTER_OPTIONS.types`), `WISHLIST_PRICE_RANGES` (single-select preset: `all` / `under30` / `30to50` / `over50`), `filterWishlist(items, { types, priceRange })`, and `ACTIVE_WISHLIST_FILTER_COUNT(filters)`. **Filter axes (TYPE + PRICE) are invented** — there's no Figma drawer spec for wishlist; swap them when one lands.   countryCodes.js         ← ISO 3166-1 alpha-2 country list (~245 rows) with `{iso2, name, dial}`. Exports `flagEmoji(iso2)` which derives the flag at render time from regional-indicator codepoints (no static flag table), and `DEFAULT_COUNTRY` (Jordan / +962 — the project's home market, matches `JOD` pricing throughout the storefront). Also exports **`phoneLengthFor(iso2)`** and the underlying **`PHONE_LENGTHS`** map keyed by ISO2: returns `{ min, max }` for the digit count expected AFTER the country code (Jordan / Saudi / UAE = 9 exactly; US / Canada / UK / Iraq / Egypt / India = 10 exactly; China = 11 exactly; Germany = 10–11; etc.). About 50 countries are mapped (MENA / Gulf / EU / NA / big APAC / key SSA); unmapped countries fall back to `DEFAULT_PHONE_LENGTH = { min: 7, max: 14 }` — the E.164 practical range (the dial code takes 1–3 of the 15-digit ceiling). Consumed by the auth `PhoneInput` (for `maxLength`) and by every form that validates a phone (SignUpForm / CompleteProfileForm / ContactForm). **When validating, strip the leading 0 trunk prefix and any duplicated dial code BEFORE measuring length** — otherwise a Jordan-style "0791234567" silently fails (the 0 inflates the count by one, the truncation drops a real digit, and the wire value ends up one digit short). Also exports **`parseE164(phone)`** → `{ country, local }`: the inverse — splits a stored E.164 string ("+962791234567") back into a country object + national digits by longest-dial-prefix match (dials pre-sorted length-desc so NANP "1242…" beats bare "1"). LENIENT/cosmetic — shared-dial mislabels (US vs Canada on "+1") round-trip to the same stored value since the editor rebuilds `+<dial><local>`. Used by the `/account` `EditProfileDrawer` (prefill the country picker) + `PersonalInformationCard` (show the dial code in its own slot).
```
