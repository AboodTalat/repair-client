# CLAUDE.md — `repair/src/components/`

Per-file inventory for the `repair/` frontend's `src/components/` directory, grouped by surface: `public/homePage/` (landing), `customer/*` (shop, product, cart, checkout, account, contact), `admin/*` (the `/r3pr-console` console), `accountant/*` (the `/r3pr-ledger` ledger), `delivery/*` (the `/r3pr-dispatch` surface), `shared/`, and `auth/`.

This is a **detail supplement** to the parent [`repair/CLAUDE.md`](../../CLAUDE.md) — read that first for the architecture, conventions, design system, route map, and backend contract. Keep both in sync: when you add or materially change a component here, update this file.

## `admin/dashboard/DashboardView.jsx` + `lib/adminDashboard.js`

**The dashboard fans out to SIX resolvers and every panel must stand or fall alone.** It used a bare `Promise.all`, and `repairCall` throws on `blnRequestSuccessful:false` — so a single failing panel rejected the batch, `DashboardView` caught it, and the page rendered **only** its error box. Reproduced against the running server with one bad date on the revenue call: five panels returned data and the page showed nothing. This is the console's landing page (`/r3pr-console` redirects here), so that is the whole admin console appearing to be down because one aggregate query failed.

`fetchDashboardData` now uses `Promise.allSettled`, maps each slot to `null` on failure, and returns a **`failures`** array of human labels. It throws only when *every* panel failed (auth, or the server being down), because at that point there is genuinely nothing to show. `DashboardBody` renders `PartialNotice` — an amber banner naming what's missing, with Retry — above the still-usable page.

**Name the missing panels; never let a failed panel render as an empty one.** An empty "Recent orders" that actually failed to load reads as *"no orders"* — a different and much worse message than *"couldn't load"*. That is why `failures` carries labels rather than a boolean.

Every consumer downstream was already null-safe (`salesCur?.rows || []`, `revenue?.donut || []`, …) and must stay that way — pinned by `Server/src/__tests__/promoDashboard.test.ts`. Note `salesPrev` is now `null` for **two** reasons (no prior period, or the prior-period call failed); both correctly mean "no comparable base", and the existing `salesPrior30 != null` guard renders no arrow rather than a fabricated 0%.

**Six calls per mount is also six audit rows** — was, until the server-side read-audit dedupe landed (see `Server/CLAUDE.md`). Adding a seventh audited read to this page is now cheap on repeat loads but still writes on the first, so keep the fan-out deliberate.

## `admin/promo/PromoManager.jsx`

**Save surfaces the server's `warning` in an amber notice, and sets it AFTER the refetch.** The backend returns `{ promoCode, warning? }` when the saved code can't actually be redeemed (an expiry already in the past). Setting the notice *before* `fetchCodes()` lets the reload clear it — the exact ordering trap `DiscountManager` hit, which is why both files now set it last. Pinned by a test.

**A past expiry is a warning, not an error, and the drawer must not start rejecting it** — back-dating is how an admin retires a campaign whose code has been redeemed (delete is refused for those). See the promo rules in `Server/CLAUDE.md`.

**`generateCode` uses `crypto.getRandomValues`, never `Math.random`.** A promo code is a bearer token for money off and codes are semi-public (flyers, screenshots, influencer posts), so a recoverable PRNG state makes the next ones predictable. The comment's search-space argument leans on `myAppValidatePromoCode` being in `SENSITIVE_OPS` — **it is** (verified: 25 rapid guesses → 5 answered, 20 throttled), so don't remove that entry without revisiting the code length.

**`usageLimit` blank means unlimited and must send `null`, never `0`.** The backend rejects `usage_limit < 1`, so the old mock's `0` sentinel would error on every unlimited code. `toWirePayload` already does this — keep it.
